01 · DIAGNÓSTICO

Estado actual: mapa de umbrales hardcoded

La arquitectura implementa 6 agentes con ciclo ODA (observe → decide → act) conectados por un EventBus pub/sub. El problema central: ningún umbral se ajusta con la experiencia. Si el modelo produce tres falsas alarmas de drift seguidas, el contador de ventanas consecutivas sigue siendo 2. Si el mercado cambia estacionalmente, los quality gates permanecen rígidos.

02 · PROPUESTA

Tres arquitecturas en escala de complejidad

La propuesta no es un salto binario a LLMs. Es una escala gradual con trade-offs concretos en costo, determinismo y sostenibilidad. La recomendación es llegar a B transitando por A: los datos de A son los que hacen útil al LLM en B.

A

Reglas + aprendizaje de umbrales

Mantiene ODA cycle y EventBus. Añade un ThresholdOptimizer que aprende de la historia para ajustar umbrales dinámicamente. Sin LLM. Bandit algorithms + regresión logística online + Bayesian optimization.

B

Híbrida: reglas + LLM para meta-decisiones

Agentes de ejecución siguen siendo rule-based. Un LLM Meta-Agent razona sobre situaciones ambiguas, escalaciones y calibración de umbrales. Claude Haiku 4.5 por costo/latencia.

C

LLM-based total

Cada agente tiene un LLM como cerebro de decisión. Las herramientas (MLflow API, KS test, reload endpoint) se exponen como tool calls. Aprendizaje vía RAG sobre ExperienceStore.

COMPONENTE COMPARTIDO · A + B + C

ExperienceStore — base de todo aprendizaje

Tabla SQLite (o parquet en MLflow artifacts) donde todos los agentes registran sus decisiones y el outcome posterior. Es el prerequisito para cualquier aprendizaje adaptativo.

# Schema mínimo del ExperienceStore
{
  "cycle_id":          str,   # ID único del ciclo ODA
  "agent":             str,   # "MonitoringAgent", "QAAgent", etc.
  "decision":          str,   # "trigger_retrain", "pass", "fail"
  "threshold_used":    float, # valor del umbral en ese ciclo
  "context_features":  dict,  # métricas observadas (KS stats, p-vals, etc.)
  "outcome":           str,   # "beneficial" | "wasted" | "missed"
  "outcome_delay":     int    # ciclos hasta conocer el outcome
}
Implementar en: mlops_common/experience_store.py — todos los agentes llaman store.record() al final de act()
03 · MODIFICACIONES

Agentes a modificar y cómo

Cuatro agentes reciben modificaciones sustanciales en la Arquitectura A. Los otros dos (MLEngineerAgent, OrchestratorAgent) solo añaden el call a store.record().

MON

MonitoringAgent

mlops_common/agents/monitoring_agent.py
Arquitectura A + B

Actualmente usa drift_threshold=2 (ventanas consecutivas) fijo. Si hay 2 falsas alarmas seguidas, el sistema se reentrena innecesariamente. No hay registro de cuántas veces el reentrenamiento fue beneficioso.

drift_threshold = 2 → Si consecutive_drift ≥ 2: trigger_retrain
data_drift_p_value = 0.05 → Si pval < 0.05: feature drifted
Propuesta — Thompson Sampling sobre drift_threshold

Cada valor candidato de drift_threshold (1, 2, 3, 4) tiene una distribución Beta(α, β). Tras cada ciclo completo, si el reentrenamiento fue beneficioso: α += 1 (éxito) para el threshold usado. Si fue desperdiciado: β += 1 (fracaso). El agente samplea el threshold con mayor expected value antes de cada ciclo. No requiere GPU — es actualización analítica de distribuciones Beta.

QAE

QAAgent

mlops_common/agents/qa_agent.py
Arquitectura A

Los quality gates son comparaciones estáticas contra valores YAML. No hay mecanismo para detectar si el gate está siendo demasiado restrictivo (rechazando challengers que habrían mejorado producción) o demasiado laxo (aprobando modelos que luego degradan).

min_accuracy ≥ 0.90 → QA pass si accuracy ≥ umbral
min_f1 ≥ 0.90 → QA pass si F1 ≥ umbral
min_per_class_recall ≥ 0.80 → QA pass si recall/clase ≥ umbral
Propuesta — QACalibrator con SGDClassifier.partial_fit()

En lugar de comparar contra un umbral fijo, el agente entrena un SGDClassifier (regresión logística online) que predice P(modelo_en_prod_exitoso | metric_value). El "threshold" se convierte en el percentil de la distribución histórica que maximiza el F1 del gate (balancear falsos rechazos vs. falsas aprobaciones). Reentrenamiento incremental con partial_fit() tras cada ciclo completo. Modelo <1KB de parámetros, totalmente interpretable.

PERF

PerformanceDriftDetector

drift-detector/performance_drift_detector.py
Arquitectura A

Tiene 5 umbrales que interactúan entre sí: p-value, effect_size, ewma_alpha, ewma_divergence, y min_samples. Optimizarlos manualmente es inviable porque el espacio de combinaciones es continuo y multidimensional.

effect_size_threshold 0.05 → |current - baseline| > threshold
p_value_threshold 0.05 → t-test p < threshold AND abs_change > 0.02
ewma_alpha 0.3 → peso del MA exponencial
EWMA divergence 0.07 → ewma_change > threshold → drift
Propuesta — Optuna Bayesian Optimization (script semanal offline)

Un script offline corre optuna.create_study() sobre el historial del ExperienceStore. Objective: F1 del detector (precision × recall de alarmas reales vs. falsas) sobre ventanas etiquetadas. Cada semana, Optuna explora el espacio de los 5 umbrales con ~50 trials y escribe el resultado al YAML de config. El detector recarga los valores en el siguiente restart. Sin cambiar el código del detector — solo se actualiza la config.

DS

DataScientistAgent + ModelSelector

mlops_common/agents/data_scientist_agent.py
Arquitectura B

Actualmente usa cfg.model.family fijo (random_forest_classifier). No considera el tipo de drift detectado, la magnitud del cambio de distribución ni las características del nuevo batch de datos para elegir familia de modelo o hiperparámetros.

Propuesta — ModelSelectorAgent con RAG sobre ExperienceStore (Arquitectura B)

Un wrapper del DataScientistAgent consulta al LLM (Claude Haiku 4.5) con few-shots extraídos del ExperienceStore: "dado que driftearon estas features con esta magnitud, y el último retrain con RandomForest tuvo accuracy X, ¿qué familia de modelo y hiperparámetros recomiendas?". Los few-shots son los 5 ejemplos más similares recuperados por embeddings de contexto. El LLM devuelve JSON estructurado con model_family y params. El DataScientistAgent usa esa sugerencia o su default si el LLM falla.

Agentes sin cambios sustanciales: OrchestratorAgent, MLEngineerAgent y HumanProxyAgent solo añaden el call a store.record() al final de act(). Su lógica de decisión es correcta y no depende de umbrales calibrables. En Arquitectura B, el OrchestratorAgent se reemplaza por un MetaOrchestratorAgent que usa LLM para situaciones ambiguas.
04 · APRENDIZAJE

Procesos de entrenamiento por componente

Cada componente adaptativo usa un método distinto, apropiado a la naturaleza de su problema de optimización y al volumen de datos disponible.

BANDIT · ONLINE

ThresholdOptimizer — MonitoringAgent

Algoritmo: Thompson Sampling sobre distribuciones Beta(α, β) por cada valor candidato de umbral.

Cuándo: al final de cada ciclo completo del runner, tras conocer el outcome del reentrenamiento.

Datos: historial del ExperienceStore — no requiere batch mínimo, funciona desde el primer registro.

Costo: actualización analítica, microsegundos. Sin GPU. Sin dependencias externas.

Monitoreo: loguear α/(α+β) por umbral a MLflow experiment threshold-optimization.

LOGISTIC REGRESSION · INCREMENTAL

QACalibrator — QAAgent

Algoritmo: sklearn.SGDClassifier con partial_fit() — regresión logística online, interpretable.

Cuándo: cada N ciclos completos (N=10 sugerido). Requiere al menos 20 ejemplos etiquetados.

Features: (metric_value, gate_name, model_family, dataset_size) → label: prod_success.

Costo: CPU, segundos. Modelo <1KB. Persistido en disco entre reinicios.

Monitoreo: F1 del calibrador logueado a MLflow experiment qa-calibration.

BAYESIAN OPTIMIZATION · OFFLINE SEMANAL

DriftHyperOptimizer — PerformanceDriftDetector

Algoritmo: Optuna TPE sampler sobre 5 hiperparámetros continuos del detector.

Cuándo: script semanal offline (cron job GitHub Actions). No bloquea el pipeline principal.

Objective: F1(detector) = harmonic mean de precision y recall de alarmas reales vs. falsas sobre historial etiquetado.

Costo: ~50 trials × evaluación sobre historial. CPU, ~5-30 min semanales.

Salida: escribe valores optimizados al YAML de config. El detector los recarga en el siguiente restart.

GRADIENT BOOSTING · BATCH PERIÓDICO

RetainDecisionModel — RetainTrigger

Algoritmo: XGBoost — predice si promover el challenger dado el contexto del retrain.

Features: (drift_magnitude, features_drifted, dataset_size, days_since_last_retrain, challenger_delta).

Label: promoted_was_beneficial — determinado a posteriori por degradación o mejora en producción.

Cuándo: reentrenar cuando acumulen ≥50 eventos de retrain etiquetados (~mensual inicialmente).

Costo: CPU, minutos. El modelo reemplaza a MIN_DELTA como criterio de decisión.

Feedback demorado — el reto principal: en todos los casos, el outcome de una decisión (¿fue beneficioso el reentrenamiento?) se conoce varios ciclos después de la decisión. El ExperienceStore debe guardar el cycle_id para poder hacer join entre decisión y outcome cuando este arrive. Los componentes de aprendizaje deben tolerar este delay y no actualizar sus parámetros hasta tener el outcome completo.
05 · LLM-BASED AGENTS

¿Cuándo y cómo incorporar un LLM?

No todos los agentes se benefician igual de un LLM. El criterio es: ¿el problema requiere razonamiento sobre contexto abierto o simplemente optimizar un parámetro continuo? Los umbrales estadísticos son optimización — el LLM no añade valor. Las meta-decisiones sobre escalación y selección de estrategia son razonamiento — el LLM sí añade valor.

Agente ¿Mover a LLM? Justificación Modelo sugerido
MON MonitoringAgent NO El problema es optimizar un umbral continuo. Bandit/Bayesian es más eficiente y determinista que un LLM para eso. —
PERF PerformanceDrift NO Multidimensional pero numérico — Optuna es la herramienta correcta. El LLM no puede optimizar sobre 5 dimensiones continuas. —
QAE QAAgent NO Calibración de umbrales de gates — regresión logística es suficiente y totalmente interpretable. —
MLOE OrchestratorAgent PARCIAL (Arq. B) La state machine cubre el 90% de los casos. El LLM interviene en escalaciones ambiguas: múltiples drifts simultáneos, fallas de QA con métricas borderline, contexto histórico inusual. Claude Haiku 4.5
DS DataScientistAgent PARCIAL (Arq. B) El wrapper ModelSelector usa LLM para recomendar familia de modelo e hiperparámetros iniciales dado el contexto. El entrenamiento sigue siendo determinista. Claude Haiku 4.5
HPA HumanProxyAgent SÍ (Arq. B) En modo auto, el LLM puede simular la política de aprobación humana aprendida de interacciones pasadas. Reduce intervención manual en casos rutinarios. Claude Haiku 4.5
ARQUITECTURA B · DETALLE

MetaOrchestratorAgent — LLM como árbitro de incertidumbre

El OrchestratorAgent mantiene su state machine para el 90% de los casos. Cuando la confianza del ThresholdOptimizer es baja (alta varianza en la distribución Beta del bandit) o cuando llegan múltiples eventos de drift simultáneos, el MetaOrchestratorAgent consulta al LLM:

contexto = {
  "drift_report":        drift_features_y_magnitudes,
  "threshold_confidence": bandit.get_confidence(),   # α/(α+β) variance
  "model_metrics":       metricas_production_actuales,
  "recent_history":      experience_store.last_n(5),  # RAG
  "state":               orchestrator.state
}
decision = claude_haiku.invoke(
    system="Eres un MLOps engineer supervisando una pipeline...",
    messages=[build_decision_prompt(contexto)],
    tools=[tool_trigger_retrain, tool_request_human, tool_noop]
)
El LLM devuelve una tool call estructurada — no texto libre. El agente ejecuta la tool y registra el reasoning en el ExperienceStore para futuros few-shots.

FLEXIBILIDAD DE DISEÑO

C gana, A es la más rígida

Añadir una nueva señal de drift en A requiere código nuevo + tiempo para acumular datos de entrenamiento del calibrador. En B basta actualizar el prompt y los few-shots. En C solo se describe la señal en el system prompt. Sin embargo, A tiene la ventaja de ser completamente predecible en diseño: el comportamiento del sistema es auditable línea por línea.

FLEXIBILIDAD DE EJECUCIÓN

B y C se adaptan en tiempo real

A adapta sus umbrales de forma online pero lenta (N ciclos). B y C pueden razonar sobre una situación nueva inmediatamente, sin esperar a acumular datos. La contrapartida: en C, el determinismo se pierde — el mismo contexto puede producir decisiones distintas entre runs, lo que complica debugging y auditoría.

COSTO COMPUTACIONAL

A es drásticamente más barata en runtime

A ciclo cada 2 segundos (default del runner): A cuesta ~0 en API, B ~$0.0001–0.001 por ciclo (~$0.14–1.44/mes a 1 ciclo/min), C ~$0.001–0.01 (~$1.44–14.4/mes). En desarrollo, la situación se invierte: A requiere implementar y mantener 4 pipelines de entrenamiento ML; B y C son principalmente prompting. A mayor escala de modelos gestionados, la ventaja de A en runtime crece linealmente.

SOSTENIBILIDAD AMBIENTAL

Paradoja: B/C pueden ser más verdes en desarrollo

A runtime, A es la más eficiente si el host usa energía renovable. Pero el desarrollo de A requiere ciclos computacionales semanales (Optuna, reentrenamiento XGBoost, evaluación de calibradores). B y C eliminan esos ciclos. Los datacenters de Anthropic operan con ~100% energía renovable, por lo que el trade-off real depende de la fuente eléctrica del host de A.

07 · IMPLEMENTACIÓN

Roadmap recomendado

La secuencia importa: los datos del ExperienceStore son el prerequisito para que el LLM en B sea útil. Sin historial, el meta-agent improvisa sobre contexto vacío.

1

ExperienceStore — prerequisito de todo lo demás

Nuevo módulo mlops_common/experience_store.py. Tabla SQLite con schema fijo. Modificar los 6 agentes para llamar store.record() al final de act(). Añadir lógica de resolución de outcome diferido (join por cycle_id cuando llega el feedback). Duración estimada: 1–2 días.

2

ThresholdOptimizer — MonitoringAgent (Bandit)

Módulo mlops_common/threshold_optimizer.py. Thompson Sampling sobre drift_threshold. Integrar al final del ciclo en runner.py. Loguear distribuciones Beta a MLflow. Duración estimada: 1 día.

3

QACalibrator — QAAgent (regresión logística online)

Modificar qa_agent.py para usar percentiles calibrados en lugar de umbrales YAML fijos. SGDClassifier.partial_fit() cada N=10 ciclos. Persistir modelo calibrador en disco. Duración estimada: 1–2 días.

4

DriftHyperOptimizer — script semanal offline (Optuna)

Script independiente scripts/optimize_drift_thresholds.py. Cron job en .github/workflows/. Lee ExperienceStore, corre 50 trials de Optuna, escribe al YAML de config. El PerformanceDriftDetector no se modifica — solo recarga config en el siguiente restart. Duración estimada: 1 día.

5

[Arquitectura B] MetaOrchestratorAgent — LLM para escalaciones ambiguas

Una vez que el ExperienceStore tiene ≥100 registros etiquetados (~2–4 semanas de operación): implementar el MetaOrchestratorAgent con Claude Haiku 4.5, RAG sobre ExperienceStore, y fallback a la state machine original si el LLM falla o el timeout se supera. Duración estimada: 2–3 días.

6

[Arquitectura B] ModelSelectorAgent — LLM para selección de modelo

Wrapper del DataScientistAgent con few-shots por similaridad de contexto. El LLM recomienda familia de modelo e hiperparámetros iniciales. Fallback a config por defecto. Duración estimada: 1–2 días.

7

[Opcional / Arquitectura C] Evaluación de LLM total

Solo si se identifican casos de uso que requieren razonamiento abierto: soporte multi-dominio, auditoría regulatoria con explicaciones en lenguaje natural, o onboarding de nuevos modelos sin tiempo para acumular historial. El costo operativo de C (~$1.44–14.4/mes) es manejable; el riesgo es el no-determinismo y la dependencia de disponibilidad del API. Evaluar contra A+B antes de migrar.

Recomendación final: implementar Arquitectura A completa (pasos 1–4) como base sólida. El ExperienceStore con ≥100 registros etiquetados es el dato que hace útil al LLM en B — sin él, el meta-agent razona sobre contexto vacío. Arquitectura C solo si aparecen requisitos de razonamiento abierto que A+B no cubren. El no-determinismo de C es un costo real en sistemas de producción que requieren auditoría o certificación.
