Sección 01

Mapeo Agente ↔ Servicio Docker

Cada agente del sistema no es un contenedor adicional — es la abstracción de software de un servicio Docker que ya existe. El runner instancia los 6 agentes en un mismo proceso Python y los conecta vía EventBus en memoria.

Agente Rol (Eken et al.) Servicio Docker Responsabilidad
MonitoringAgent MON drift-detector Detecta data drift (KS-test) y performance drift por ventanas consecutivas
OrchestratorAgent MLOE nginx + GitHub Actions Coordina el pipeline completo; gestiona la máquina de estados global
DataScientistAgent DS model-trainer + mlflow Entrena modelos vía mlops_common, registra en MLflow
QAAgent QAE test-runner Valida métricas del modelo contra quality_gates del YAML
HumanProxyAgent Human Operador / CI manual Aprobación o rechazo antes de promover a producción
MLEngineerAgent MLE inference-api (:8000) Hot-swap del modelo sin downtime vía POST /reload
ℹ
EventBus en memoria: en esta implementación el bus es síncrono y en proceso. Para agentes distribuidos en múltiples hosts, reemplazar EventBus con un adaptador a Redis Streams, NATS o RabbitMQ — la interfaz publish() / subscribe() no cambia.
Sección 02

Levantar el Stack Docker

El sistema agéntico requiere que los servicios estén corriendo antes de ejecutar el runner. El orden importa: MLflow debe estar healthy antes de que cualquier agente intente registrar o leer modelos.

Arranque paso a paso bash · mlops-stack/ 
# ── Paso 1: levantar MLflow (registro de modelos)
docker compose up -d mlflow
# verificar que está healthy:
docker compose ps

# ── Paso 2: entrenamiento inicial (una sola vez)
docker compose run --rm model-trainer

# ── Paso 3: levantar inference, proxy y monitor
docker compose up -d inference-api nginx drift-detector
⚠
TLS requerido: nginx necesita certificados antes de arrancar. Generarlos con bash generate-certs.sh localhost si no existen. Solo la primera vez.
mlflow Puerto expuesto

Vinculado a 127.0.0.1:5001 — solo accesible desde el host local. Todos los agentes lo usan como tracking URI interna.

inference-api Puerto expuesto

Vinculado a 127.0.0.1:8000. El único punto público es nginx en 443. El agente MLE llama directamente a /reload.

model-trainer Contenedor efímero

No es un servicio de larga duración — es un job que corre y termina. El agente DataScientist replica esta lógica internamente.

drift-detector Loop permanente

Corre en background revisando drift periódicamente. En modo agéntico, el MonitoringAgent reemplaza este loop con ciclos discretos observe→decide→act.

Sección 03

Ejecutar el Runner Multi-Agente

mlops_common/agents/runner.py instancia los 6 agentes, los conecta al EventBus y ejecuta N ciclos del pipeline completo. Tiene dos modos de operación.

Modo automático — sin intervención humana bash 
# Recomendado: dentro de Docker (tiene acceso a los servicios internos)
docker compose run --rm model-trainer \
  python -m mlops_common.agents.runner \
  --auto-approve \
  --cycles 5 --interval 2.0 \
  --mlflow-uri http://mlflow:5001 \
  --api-url http://inference-api:8000 \
  --log-level INFO
Modo interactivo — con aprobación humana bash 
# Requiere -it para input interactivo
docker compose run --rm -it model-trainer \
  python -m mlops_common.agents.runner \
  --cycles 5 \
  --mlflow-uri http://mlflow:5001 \
  --api-url http://inference-api:8000

# Cuando QA pasa, el runner se pausa:
  [runner] HUMAN DECISION REQUIRED
  [runner] Model details: {run_id: ..., metrics: {...}}
  Approve? [y/n]: y
Parámetros del runner CLI reference 
--auto-approve       omite la aprobación humana (HumanProxy en modo auto)
--cycles N           número de ciclos observe→decide→act (default: 5)
--interval N         segundos entre ciclos (default: 2.0)
--drift-threshold N ventanas consecutivas para disparar retrain (default: 2)
--mlflow-uri URL     URI del tracking server (default: http://mlflow:5001)
--api-url URL        URL del inference-api (default: http://inference-api:8000)
--log-level LEVEL    DEBUG | INFO | WARNING (default: INFO)
✓
Desde fuera de Docker: si tienes el entorno Python local con pip install -e mlops-stack/, correr directamente con python -m mlops_common.agents.runner --mlflow-uri http://localhost:5001 --api-url http://localhost:8000 también funciona.
Sección 04

Flujo Completo — Ciclo de 10 Pasos

En cada ciclo del runner, los agentes se ejecutan en orden fijo: MON → ORCH → DS → QA → Human → MLE. Cada uno corre su ciclo observe → decide → act y publica eventos en el EventBus que activan a los agentes siguientes.

01
MonitoringAgent · MON · drift-detector
Observa el sistema y detecta drift
observe() — carga el dataset de referencia desde la config YAML, consulta /health del inference-api, y ejecuta KS-test por feature contra muestras actuales.

decide() — si consecutive_drift >= drift_threshold (default 2), decide trigger_retrain.

act() — publica drift.detected en el EventBus con la lista de features afectadas.
→ drift.detected
02
OrchestratorAgent · MLOE · nginx + CI/CD
Recibe drift → activa reentrenamiento
observe() — drena la cola de eventos recibidos vía on_message().

decide() — si recibe drift.detected y estado es idle, decide trigger_retrain.

act() — publica retrain.triggered y transiciona su estado: idle → retraining → qa_pending.
→ retrain.triggered
03
DataScientistAgent · DS · model-trainer + mlflow
Entrena y registra el modelo challenger
Recibe retrain.triggered vía suscripción.

act() ejecuta el pipeline completo: load_config() → get_data_source() → get_model_strategy() → train_test_split() → fit() → compute_metrics() → mlflow.log_*.

Al finalizar publica model.trained con run_id, métricas y metadata del config.
→ model.trained
04
QAAgent · QAE · test-runner
Evalúa quality gates del modelo
Recibe model.trained con las métricas calculadas.

act() — itera sobre quality_gates del YAML (ej. min_accuracy: 0.90, min_f1: 0.90) y compara contra las métricas del modelo. Acumula failures.

Si todo pasa → qa.passed. Si algún gate falla → qa.failed y el pipeline se detiene.
→ qa.passed | qa.failed
05
OrchestratorAgent — decisión de aprobación
QA pasó → solicitar aprobación o promover auto
Recibe qa.passed con estado qa_pending.

Si auto_approve=True → decide promote y publica model.promoted directamente.

Si auto_approve=False → decide request_approval, publica approval.requested y transiciona a approval_pending.
→ approval.requested | model.promoted
06
HumanProxyAgent · Human · Operador
Aprobación humana (si no es auto-approve)
El runner se pausa y muestra en consola los detalles del modelo. El operador responde y o n.

approve() → llama orchestrator.approve() → publica model.promoted.

reject(reason) → llama orchestrator.reject() → publica model.rejected → pipeline regresa a idle.
→ model.promoted | model.rejected
07
MLEngineerAgent · MLE · inference-api
Hot-swap del modelo — sin downtime
Recibe model.promoted vía suscripción.

observe() — consulta /health e /info del inference-api para verificar que está disponible.

act() — ejecuta POST inference-api:8000/reload. La API carga el modelo Production más nuevo desde MLflow sin reiniciar el contenedor. Publica model.reloaded.

El Orchestrator recibe model.reloaded → estado vuelve a idle. Pipeline completo.
→ model.reloaded
Sección 05

Configuración YAML — Control del Comportamiento

El archivo configs/iris-classifier.yaml (montado en /app/configs/ dentro de los contenedores) es el único punto de configuración que todos los agentes leen. Cambiar el YAML cambia el comportamiento del pipeline sin tocar código.

quality_gates → QAAgent yaml 
quality_gates:
  min_accuracy: 0.90   # QA falla si < 0.90
  min_f1: 0.90
  min_per_class_recall: 0.80
  max_cv_std: 0.05     # QA falla si > 0.05
drift → MonitoringAgent yaml 
drift:
  data_drift_p_value: 0.05  # umbral KS-test
  performance:
    consecutive_windows: 2 # = --drift-threshold
    p_value_threshold: 0.05
model → DataScientistAgent yaml 
model:
  family: random_forest_classifier
  params:
    n_estimators: 200
    max_depth: 8
    random_state: 42
Cambiar caso de uso bash 
# Regresión + CSV + DVC en lugar de Iris
docker compose run --rm \
  -e MODEL_CONFIG=/app/configs/custom-regressor-dvc.yaml \
  model-trainer \
  python -m mlops_common.agents.runner \
  --auto-approve
ℹ
Variable de entorno MODEL_CONFIG: todos los agentes llaman load_config() que lee esta variable. Si no está definida, usa /app/configs/iris-classifier.yaml como default. Permite múltiples casos de uso en el mismo stack sin modificar código.
Sección 06

Quick Start — Todo Junto

Secuencia completa desde cero: infraestructura, entrenamiento inicial, y ejecución del sistema agéntico en modo automático.

Secuencia completa bash · mlops-stack/ 
# ── 0. Prerrequisito: generar certs TLS (solo la primera vez)
bash generate-certs.sh localhost

# ── 1. Levantar infraestructura
docker compose up -d mlflow
docker compose run --rm model-trainer           # entrenamiento inicial
docker compose up -d inference-api nginx drift-detector

# ── 2. Verificar que todo está up
docker compose ps
  mlflow          healthy
  inference-api   healthy
  nginx           running
  drift-detector  running

# ── 3. Ejecutar el sistema agéntico (5 ciclos, auto-approve)
docker compose run --rm model-trainer \
  python -m mlops_common.agents.runner \
  --auto-approve \
  --cycles 5 \
  --interval 2.0 \
  --log-level INFO

# ── 4. Salida esperada (resumen de eventos al final):
  DEMO COMPLETE — N events in history:
  [monitoring]      drift.detected     → {drifted_features: [...]}
  [orchestrator]    retrain.triggered  → {reason: ...}
  [data_scientist]  model.trained      → {run_id: ..., metrics: {...}}
  [qa_engineer]     qa.passed          → {run_id: ..., primary_value: 0.97}
  [orchestrator]    model.promoted     → {}
  [ml_engineer]     model.reloaded     → {status: ok, version: 2}
Comandos de diagnóstico bash 
# Ver logs de un agente específico
docker compose logs drift-detector --tail 50

# Verificar que inference-api tiene el modelo más nuevo
curl http://localhost:8000/info

# Forzar hot-reload manual del modelo
curl -X POST http://localhost:8000/reload

# Correr solo las pruebas de calidad (como lo haría QAAgent)
docker compose run --rm test-runner
✓
El historial del EventBus al final de la demo es la traza completa del pipeline agéntico. Cada línea es un AgentMessage con sender, topic y payload — útil para auditoría y debugging del flujo.
