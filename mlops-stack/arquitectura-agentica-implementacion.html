Implementación de la Arquitectura Agéntica

Traducción del diseño multi-agente conceptual (Eken et al. §3.3) a un framework rule-based en Python: observe() → decide() → act() sobre el stack MLOps Docker Compose existente.

Rule-based · observe → decide → act mlops_common/agents/ 6 agentes · EventBus pub/sub
Parte 01

Estructura del Framework

El framework vive en mlops_common/agents/ — el mismo paquete compartido por todos los servicios Docker. Cada agente es una clase Python que hereda de AgentBase y se comunica con los demás vía EventBus.

# Estructura del paquete mlops_common/agents/ __init__.py # AGENT_REGISTRY + exports base.py # AgentBase ABC + dataclasses event_bus.py # EventBus pub/sub orchestrator_agent.py # MLOE — coordina todo data_scientist_agent.py # DS — entrena modelos ml_engineer_agent.py # MLE — sirve/recarga modelo qa_agent.py # QAE — quality gates monitoring_agent.py # MON — detecta drift human_proxy_agent.py # HUMAN — punto de aprobación runner.py # Demo: orquesta todos los agentes
Principio de diseño
Los agentes no duplican la lógica existente en train.py, detector.py o app.py. Son una capa de coordinación que envuelve esos servicios, formalizando sus interacciones como un sistema multi-agente explícito.
Parte 02

El Ciclo observe → decide → act

Todo agente implementa tres métodos abstractos que forman un ciclo determinístico. A diferencia de agentes LLM (que razonan con un modelo de lenguaje), estos agentes son rule-based: las reglas de decisión son código Python explícito, predecible y auditable.

ABC

AgentBase — la clase base

Cada agente hereda de AgentBase e implementa los tres métodos del ciclo. El método run_cycle() los ejecuta en secuencia.

class AgentBase(ABC): def __init__(self, name, role, bus): self.name = name # "monitoring", "data_scientist", ... self.role = role # "MON", "DS", "MLE", "QAE", "MLOE" self.bus = bus # EventBus compartido @abstractmethod def observe(self) -> Observation: ... # ¿Qué ve del sistema? @abstractmethod def decide(self, obs) -> Decision: ... # ¿Qué decide hacer? @abstractmethod def act(self, dec) -> ActionResult: ... # ¿Qué ejecuta? def run_cycle(self) -> ActionResult: obs = self.observe() dec = self.decide(obs) if dec.action == "noop": return return self.act(dec)
EstructuraCamposPropósito
Observation data: dict, timestamp Snapshot del estado del sistema en un instante
Decision action: str, reason: str, params: dict Qué hacer y por qué (auditable)
ActionResult success: bool, detail: str, artifacts: dict Resultado de la ejecución
AgentMessage topic, payload, sender, timestamp Mensaje inter-agente vía EventBus
Parte 03

EventBus: comunicación inter-agente

El EventBus implementa el patrón pub/sub en memoria. Cada agente publica AgentMessage en tópicos; los agentes suscritos reciben el mensaje como callback. El bus mantiene un historial completo para auditoría.

# Uso del EventBus bus = EventBus() # Agente MON publica cuando detecta drift mon.publish("drift.detected", {"features": ["petal_width"]}) # El orquestador, suscrito a drift.detected, recibe el mensaje # automáticamente via on_message() y reacciona en su próximo ciclo
Extensibilidad
Para escalar a múltiples hosts, reemplazar EventBus por un adaptador a Redis Streams, NATS o RabbitMQ. La interfaz publish()/subscribe() no cambia — los agentes no saben si el bus es local o distribuido.
Parte 04

Los 6 Agentes Implementados

Cada agente mapea 1:1 al rol de Eken et al. y al servicio Docker de la sesión conceptual. Aquí se muestra qué hace cada uno en su ciclo observe → decide → act.

🎛️
OrchestratorAgent
MLOE — orchestrator_agent.py
Máquina de estados: idle → retraining → qa_pending → approval_pending → promoting → idle
  • observe() — drena eventos pendientes del inbox
  • decide() — evalúa la máquina de estados según el evento recibido
  • act() — publica retrain.triggered, approval.requested, o model.promoted
  • Métodos adicionales: approve() / reject() para el humano
Suscrito a: drift.detected, qa.passed, qa.failed, model.reloaded, system.error
🔬
DataScientistAgent
DS — data_scientist_agent.py
  • observe() — verifica si hay request de retrain pendiente
  • decide() — si retrain_requested → action="train"
  • act() — carga config, entrena con mlops_common, registra en MLflow
  • Publica: model.trained con métricas y run_id
Suscrito a: retrain.triggered
⚙️
MLEngineerAgent
MLE — ml_engineer_agent.py
  • observe() — verifica health del inference-api y versión actual
  • decide() — si reload_pending + API healthy → action="reload"
  • act() — POST /reload al inference-api (hot-swap sin downtime)
  • Publica: model.reloaded con la nueva versión
Suscrito a: model.promoted
🧪
QAAgent
QAE — qa_agent.py
  • observe() — verifica si hay un modelo nuevo para validar
  • decide() — si validation_pending → action="validate"
  • act() — evalúa métricas vs quality_gates del YAML
  • Publica: qa.passed o qa.failed
Suscrito a: model.trained
📊
MonitoringAgent
MON — monitoring_agent.py
  • observe() — calcula KS test por feature vs referencia
  • decide() — si consecutive_drift >= threshold → action="trigger_retrain"
  • act() — resetea contador y publica evento de drift
  • Publica: drift.detected
Auto-driven: no suscripciones — corre periódicamente
👁️
HumanProxyAgent
HUMAN — human_proxy_agent.py
  • observe() — verifica si hay aprobación pendiente
  • decide() — si auto_mode → aprobar; si no → esperar input humano
  • act() — en modo manual, expone approve()/reject() al operador
  • Soporta: CLI interactivo, HTTP endpoint, o auto-approve (tests)
Suscrito a: approval.requested

Parte 06

Máquina de Estados del Orquestador

El OrchestratorAgent implementa los 10 pasos del flujo como una máquina de estados finitos. Cada transición corresponde a un mensaje del EventBus.

idle
Estado inicial — esperando eventos
El sistema está en producción normal. El agente MON corre sus ciclos periódicos.
drift.detected → retraining
rtrn
retraining → publica retrain.triggered
El agente DS recibe el mensaje y entrena un nuevo modelo. Al publicar model.trained, el QAE lo recibe.
DS entrena → qa_pending
qa
qa_pending — esperando resultado de QA
El QAE evalúa las métricas contra los quality gates. Publica qa.passed o qa.failed.
QAE valida qa.passed → approval_pending qa.failed → idle
appr
approval_pending — esperando decisión humana
El HumanProxyAgent expone la decisión al operador. Si auto_approve=True, se salta este paso.
HUMAN decide approve() → promoting reject() → idle
prom
promoting — hot-swap del modelo
Publica model.promoted → el MLE ejecuta POST /reload → publica model.reloaded → vuelta a idle.
MLE recarga model.reloaded → idle
# Transiciones de estado (en orchestrator_agent.py) if topic == DRIFT_DETECTED and state == "idle": state = "retraining" if topic == QA_PASSED and state == "qa_pending": state = "approval_pending" if topic == QA_FAILED and state == "qa_pending": state = "idle" if approve() and state == "approval": state = "promoting" if topic == MODEL_RELOADED and state == "promoting": state = "idle"
Parte 07

Ejecución del Sistema

runner.py instancia los 6 agentes, los conecta al EventBus, y ejecuta ciclos en el orden natural del pipeline.

# Ejecución con auto-approve (demo sin interacción) python -m mlops_common.agents.runner --auto-approve --cycles 5 # Con aprobación manual (se detiene para input humano) python -m mlops_common.agents.runner --cycles 3 # Dentro de Docker (conectado al stack real) docker compose run --rm model-trainer \ python -m mlops_common.agents.runner \ --mlflow-uri http://mlflow:5001 \ --api-url http://inference-api:8000 \ --auto-approve
Orden de ejecución por ciclo

Cada ciclo ejecuta los agentes en el orden del pipeline

MON → Orchestrator → DS → QA → Human → MLE

Este orden refleja el flujo natural del sistema. El EventBus conecta la salida de cada agente con la entrada del siguiente: MON publica drift.detected, el Orchestrator lo recibe y publica retrain.triggered, DS entrena y publica model.trained, etc.

Extensiones posibles
LLM para decisiones ambiguas: reemplazar el decide() del HumanProxyAgent con una llamada a un LLM (Claude, GPT) que analice las métricas y sugiera al humano aprobar o rechazar — sin tomar la decisión final. Esto resuelve parcialmente el Automation Dilemma (§5.2.5) sin eliminar el control humano.
